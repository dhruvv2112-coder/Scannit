## Contract feedback on PR #1 / #3 (not yet posted on those PRs)
1. **Up-axis handoff.** `mesh_artifact.frame` is `+Z` up (`LOCAL_ZUP`), but glTF 2.0 and the browser viewer are `+Y` up. Proposal: the scene/survey frame stays Z-up, and every GLB handed to the viewer is converted with a documented −90° rotation about X at export. The artifact also records the viewer frame (`up_axis: +Y`, `handedness: right`, `from_frame: scene`), or a `transform` from `scene` to `gltf`. XR-002 will implement the viewer side either way, but one agreed convention avoids mirrored or tipped-over models.
2. **Media type.** The example mesh is `model/ply`. Please allow `model/gltf-binary` (GLB) in `mesh_artifact` as the viewer delivery format, with PLY staying the reconstruction intermediate. The viewer will not load PLY tiles in production.
3. **Reference length.** For the 1.000 m software-scale gate, add an optional `reference_lengths: [{id, length_m, endpoints_m: [[x,y,z],[x,y,z]], frame_id}]` field (on `quality_report` or `mesh_artifact`) so the viewer can overlay and check it. This checks scaling only; surveyed checkpoint accuracy stays with account 1.
4. **Tracker IDs.** #1's `features.csv` has no viewer rows, and #3 adds a different `features.csv` with `VWR-001…005`. Account 3's brief uses `XR-001…010`. Please settle on one tracker file and one ID scheme; mapping `XR-001 → VWR-001` is fine.
5. **Handoff path.** #3 adds `docs/project_plan/handoffs/account3/`, while account 3's brief uses `docs/handoffs/account3/`. Account 3 will follow whichever the merged plan picks.

XR-001 (#4) touches only `apps/web`, `tests/viewer`, `docs/xr`, `docs/handoffs/account3` and a path-scoped `.github/workflows/xr-web.yml`, so it doesn't conflict with `ci.yml`.
